# Security

Local-only tool. Threat model: prompt injection from postings/web pages, credential leakage, accidental submission, other local processes.

- Backend binds 127.0.0.1; Host/Origin allowlists, signed 30-day cookie sessions, CSRF, per-start bearer read token.
- Submit approvals are written only by the authenticated human-session route and bind to the current draft hash (code-verified in toolbox mode, agent-reported in direct mode). Agents cannot create approvals. Direct final Submit is governed by instructions and server-side detection, not a browser-level guard. Authorized runs commit a durable submit-click fence before the model; uncertainty goes to the owner. Unapproved reports are recorded as submitted-as-reported, fenced against repeat submission, and surfaced in Needs You.
- The authenticated, CSRF-protected `user-confirmed` route records a human report of an application submitted outside automation. It intentionally allows missing automated verification/approval: when no draft hash exists, Services supplies the placeholder `"user"` as both gate hashes, with `user-confirmed` evidence. This is an audited human attestation, not a verified draft or a submit approval. It records completion without clicking a submit control; agents cannot invoke it. An authorized automated submit run requires a server-written approval bound to the current draft hash.
- Passwords are generated by the backend and stored in macOS Keychain. DB stores `secret_ref` only. `jp browser fill-secret` accepts a raw ref, checks its recorded origin, and injects over stdin. 1Password/Bitwarden adapters are planned, not implemented.
- Secrets must not enter DB, vault, git, logs, prompts or events. Verification failure keys/kinds go to the model; diagnostic plan values remain in server-side job events.
- Postings/pages are untrusted data. CAPTCHA, MFA and email codes require the user. Board policies control automated versus assisted/manual submission.
- Workers run separately from HTTP, with persisted Start/Stop and daily admission budgets. Toolbox browser commands are paced; direct browser actions have no per-action pacing hook. Token allowances are admission controls, not a hard bound on an individual model call's actual tokens.
- In toolbox mode, `JP_ROLE=agent` is an environment-only CLI guard, not an authentication or OS security boundary. The operational barrier for Haiku is Claude's `--allowedTools Bash(<absolute jp path> *)` policy plus a scrubbed environment, disabled other tools/MCP/config sources and the deterministic server gates. Claude inherits only HOME, a constructed tool PATH, LANG and JP_ROLE/JP_JOB/JP_WORKER; DB passwords/DSNs, arbitrary `.env` variables and inherited API credentials are excluded. `bin/jp` loads its own `.env` inside the toolbox subprocess. This assumes the installed CLI enforces its tool policy and the local account/tool binaries are trusted; an arbitrary local process can change JP_ROLE and access that account's config.
- Direct mode (default; [ADR 0015](docs/adr/0015-direct-browser-harness.md)) gives Haiku all browser-harness helpers, raw CDP and any tab in shared Chrome. Bash is restricted to the absolute `bin/jp-harness` launcher; its deny-default macOS sandbox is mandatory with no unsandboxed fallback. Python and its inherited daemon can read their resolved runtime/system libraries and exactly one CV, read/write only node-local `BH_HOME` state, connect only to the configured loopback CDP port and a fresh per-run Unix socket, and execute only their interpreter. No Security/Keychain mach lookups are allowed. No rules grant access to home SSH/Keychains/Claude/config, repo `.env`, or other vault/DB/backup files. Claude retains its own login access outside the Python sandbox. Child environments exclude DSNs/Redis/secrets; the launcher scrubs again. Telemetry and recordings are off. Strict bounded result validation rejects unknown keys, secret field labels and recognizable credential values; arbitrary prose cannot be proven secret-free. Backend logs record status/counts, never prompts/raw results; direct mode disables raw agent-debug output.
- The sandbox contains Python, not Chrome or CDP browser capabilities. Browser navigation, cookies, raw CDP upload/download and cross-tab access remain available; this is not browser data-loss prevention. The model is instructed never to create accounts, type/return secrets, or submit outside an approved run. Direct reported draft/confirmation evidence is labeled explicitly rather than claimed code-verified. The server validates reports and scans known confirmation patterns, including on invalid-output/timeout paths; an unknown confirmation or a disappeared tab can evade detection. Live sandbox startup, daemon inheritance, denial probes and headless heredoc tool authorization must be tested before operational reliance.
- Pool-wide environment failures use the Claude exit code, structured JSON error metadata and stderr only. Model result/page prose is never used for classification or included in Claude failure diagnostics. A structured per-run budget/turn limit blocks that job and leaves the pool enabled; invalid/no-JSON output on exit zero also fails only that job unless a separate environment signal exists. Missing/invalid usage is settled in `finally` as an explicit conservative cost/token estimate using the reserved allowance. A hard process kill or DB outage can still leave an unsettled reservation charged until UTC rollover.
- Backups contain the full vault (CVs, postings, notes and history) and the DB dump. The `backup` Compose service (`docker/backup.sh`, ADR 0022) writes mode-0600 `.tar.gz` bundles into the mode-0700 `data/backups/` and keeps the newest 14. They are **not encrypted** (the previous `age` option was not carried over: the Postgres image has no `age`); they rely on FileVault for encryption at rest, and permissions alone do not encrypt them, so any off-machine copy needs separate protection.

`.github/workflows/ci.yml` runs on pushes, pull requests, manual dispatch and a weekly schedule. It checks ruff lint and formatting, strict mypy, frontend TypeScript and build, audits the pinned Python requirements with pip-audit and pnpm's locked dependencies with pnpm audit (all reported severities), and scans fetched git history plus checked-out files using Gitleaks with redacted output. Audit failures fail CI. Gitleaks uses the standalone checksum-verified CLI release, without the licensed GitHub action. Jobs use read-only repository permissions. CI does not start workers, connect to job sites, create approvals or exercise submission behavior.

The Python requirements snapshot pins versions but currently has no artifact hashes; a fresh universal `uv.lock` and online audit results remain unverified because this managed shell cannot resolve PyPI. CI must run successfully on GitHub before claiming clean vulnerability/secret scans. Dependabot proposes weekly pip, npm/pnpm and Actions updates; maintainers must refresh/review the Python snapshot when changing pyproject dependencies. The pinned Gitleaks CLI and audit-tool version need manual updates. pnpm 11 version-update support is outside GitHub's currently documented pnpm 7–10 range ([GitHub supported ecosystems](https://docs.github.com/en/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories)); CI's pnpm audit still runs independently.

## Dashboard session

Open `http://127.0.0.1:4100` directly; no start token is required or printed. Starlette SessionMiddleware signs the `jp_session` cookie using a persistent random secret in `data/.session-secret`. The file is created exclusively without following symlinks, with mode 0600; existing permissions are repaired to 0600 before reading. The cookie lasts 30 days, is HttpOnly and SameSite=Strict, and uses path `/`. Secure is disabled because this service uses plain HTTP on loopback. The signing secret survives server restarts and reboots and is never logged. The signed cookie contains only the session's CSRF token, not application credentials.

Only a document navigation to `/` with `Sec-Fetch-Site: none` or `same-origin` and `Sec-Fetch-Dest: document` can create a session, after the Host allowlist check. Missing fetch metadata, `same-site`, and `cross-site` requests cannot mint sessions. Browsers supply these headers and page JavaScript cannot forge them. `GET /api/session` only returns an existing session's CSRF token; otherwise it returns 401. It still rejects a supplied disallowed Origin. The dashboard retries through `/` once, with a sessionStorage guard, then shows a normal-browser instruction if authentication still fails.

Every non-GET/HEAD request authenticated with the cookie still requires an allowlisted Origin and a constant-time CSRF match. The Host allowlist prevents DNS rebinding, and the existing CSP and SameSite protections remain. Bearer authentication cannot create a human session or approve submissions. Ordinary curl requests carry no fetch metadata and receive no session.

The local owner account is trusted: an arbitrary process running as that account can already read `.env` and write approvals directly in PostgreSQL, so a startup token adds no meaningful protection against it. Fetch metadata protects against web pages, not local tools that deliberately forge headers. Haiku runs with a scrubbed environment and only the fixed `Bash(jp *)` toolbox, with no curl access; its restrictions and the deterministic approval gates remain unchanged. See [ADR 0010a](docs/adr/0010a-open-dashboard.md).

Report issues privately to the repository owner.

## Raw agent-browser for the worker

The Haiku worker uses the real `agent-browser` CLI, on any site, through the shim `bin/agent-browser`
(first on the worker PATH). The shim pins `--session jp-<job>`, `--action-policy agent/browser-policy.json`
(default deny, explicit allow-list of interaction/read actions; no `evaluate`, cookies, storage, network,
state, download, auth), `--init-script agent/submit-guard.js`, `--content-boundaries` and `--max-output`,
and refuses agent-supplied session/policy/CDP/profile/extension/proxy/config options and administrative
commands. `upload` accepts only the job's exact CV object path. Every command is recorded as a
`browser_cmd` event (verb + target + value length, never typed text), is paced, counts against a per-job
action cap, and any mutating command clears `verified_at`/`draft_hash`, so an approval can never cover an
agent edit. `jp verify` adopts live non-secret values into the plan as `source=agent`, so they are part of
the draft hash and visible at approval. Pages and snapshots are untrusted data. The worker model is Haiku
only; there is no model escalation.

### Residual risks accepted by the owner
1. **Submit guard is page-level JavaScript.** `agent/submit-guard.js` blocks click/Enter/implicit submit on
   the final control until `jp browser submit` unlocks it, but a prompt-injected agent could in some cases
   submit without approval. Mitigation: after every agent run code checks the confirmation patterns; a
   confirmation without a `submit_clicked` event marks the job "SUBMITTED WITHOUT APPROVAL", disables
   automation and shows it red in the dashboard.
2. **A password filled by `jp browser fill-secret` sits in the page DOM** and the agent could read it back.
   Mitigation: passwords are generated, unique per site, and used only for job-site accounts; Keychain
   storage and origin binding are unchanged.

## Account creation (ADR 0028)

The agent may create an employer-site account (SSO first, else a generated password). The password is generated and
filled inside the page by one verbatim `run` helper and never enters the model context, tool results, the database,
events, prompts or logs; Chromium stores it after the owner clicks Save on its prompt. Server defenses: strict result
schema (`account` = created + method only), any password-named key refused, password-like owner answers refused, profile
email check on the generated path. **Residual risk accepted by the owner (2026-10-18):** a model that deviates and
types a password with `act` fill/type leaves it in Neo's `tool_dispatches.args_json`; the server cannot prevent or
erase that. Treat such accounts as throwaway and use a unique password per site.

## Redis broker

Redis runs strictly on loopback (`127.0.0.1:6380`) with `requirepass` enabled (a 24-byte hex secret generated in `.env` mode 0600) and persistence disabled (`save ""`, `appendonly no`, `maxmemory 64mb`). It serves solely as a lossy delivery pipe for Celery.

Messages carry only a job ID string. No secrets, credentials, approvals, form values, instructions or page contents ever transit Redis. If an unauthorized local process were to forge a delivery message, it can only name a job ID: `run_job` verifies and claims the job via an atomic start in PostgreSQL (`start_run`, requiring `started_at IS NULL AND leased_by = <task id>`). If no matching lease exists, the execution exits immediately. Furthermore, actual submission remains strictly gated by the server-written approval record in PostgreSQL bound to the verified draft hash; message forgery cannot bypass the approval gate.

Celery remote control stays enabled on the job worker because the liveness ping (`node_ping`) uses it to learn whether the prefork pool answers. The consequence is bounded: a local process that holds the Redis password could stop, restart or reconfigure workers (a denial of service), and could publish a forged `run_job` for a job ID, but it still cannot start a run that PostgreSQL has not leased, create or consume an approval, or submit anything: those paths are decided only by the server-written approval bound to the verified draft hash. Keep the Redis password in `.env` (mode 0600) and Redis on loopback.

## Shared Chrome debug port

Workers' browser tabs live in one Chrome per node (ADR 0014) whose DevTools port (`127.0.0.1:9333`, `CHROME_DEBUG_PORT`) is unauthenticated: any local process can drive every tab, including a parked, filled application form. It is bound to loopback only and its profile is wiped on every start. The agent cannot reach it: its Bash allowlist is `jp` plus the browser shim, which refuses `--cdp`, `connect`, `eval`, `tab`, `window`, `cookies`, `storage`, `state` and navigation to the debug port itself; page scripts cannot open the WebSocket (Chrome rejects requests that carry an `Origin`). A local process that can reach 127.0.0.1 can still read or modify those tabs, and can attempt a submit click; the page-level guard and the server-written approval bound to the verified draft hash remain the gates, but treat the local machine as the trust boundary. In the default `shared` tab mode two jobs on the same ATS origin share cookies and localStorage like several tabs of one person; set `BROWSER_TAB_ISOLATION=context` for one isolated context per job.
