# ADR 0005 — audited writes, durable projection and runtime adapters

Status: accepted (2026-10-10). Builds on ADRs 0003 and 0004.

## Decision

- Services owns mutations from HTTP, CLI, browser actions and CV tailoring. Configuration, fact, answer, profile, board and account operations include audit events in the same transaction. `job_events.job_id` is nullable for changes that have no single job; payloads identify keys/refs, excluding answer/profile/credential values.
- Migration `0002_runtime_architecture.sql` adds durable projection and CV commit queues. Triggers on jobs/applications enqueue notes atomically. The server sweeps committed work independently of requests; filesystem/git failures are logged and retried. Projection generation compare-and-delete preserves concurrent changes; session advisory locks serialize projectors without keeping a DB transaction open during filesystem work. The lock holder's connection is reused for nested queries to avoid pool exhaustion. `jp admin project` remains the explicit repair command.
- The projection single writer calls `commit_cv` under both thread and cross-process vault locks. `.tex` is recorded for objects/job links during preparation, PDFs for track versions and job links/objects at submit. Submitted/base/tailored CVs remain content-addressed immutable objects with symlinks. Existing CV versions/jobs are backfilled into commit queues by the migration. No vault remote decision is made here.
- The scheduler takes `AgentDriver`; `ClaudeDriver` contains the scoped subprocess and usage accounting. Its `worker` parameter supplies the lease identity used by agent-role CLI fencing. `Clock` is retained and implemented by `SystemClock` for worker timestamps; PostgreSQL time remains authoritative for leases/applied dates, and interruptible waits remain standard threading operations.
- JSON routes declare pydantic response models; SSE/static-file endpoints explicitly use `response_model=None`. OpenAPI export imports the app without opening its pool, starting workers or writing tokens. No public OpenAPI/docs route is enabled.
- Runtime settings live in a singleton JSONB row with pydantic validation. Updates require the UI session, and serialize against scheduler start/stop; automation must be stopped first. Environment values provide defaults. Per-call browser/CV budgets are configurable; aggregate daily budgets remain a separate unimplemented plan item.

## Browser lifecycle and Chrome boundary

Runtime sessions are tracked in DB. Blocked/idle/terminal jobs, successful fenced lease releases and expired leases close them; unsuccessful closes stay retryable. Browser operations and open/close cleanup share a per-job advisory lock, so cleanup cannot interrupt an in-flight verifier/click. A stale cleanup callback checks the current close request/lease before acting. Sessions remain live from submit click through confirmation while the lease is held. Any rebuild after approval refills the stored plan and runs verification against the approved hash. Once a submit-click event exists, tools refuse reopening/refilling the form: confirmation or human handoff only.

Installed `agent-browser --help` confirms `--profile <name|path>`, `--args` and `--cdp <port|url>`. It also explicitly states `--allowed-domains` rejects profiles/CDP. Replacing worker allowlists with CDP would weaken the existing runtime boundary. Therefore workers keep isolated allowlisted sessions. Human review is implemented separately: UI-session `POST /api/jobs/{id}/browser-review` starts dedicated Chrome with its own user-data-dir and :9223 CDP, or attaches to :9222 only when `reviewBrowser=attach` has been selected in settings. This human endpoint is not an agent tool. Persistent human Chrome is outside worker cleanup; worker sessions carry no persistent profile/restore files. Frontend controls are outside this backend batch.

## Monthly event partitions: deferred

Monthly partitioning is not a cheap forward migration: the current table has a bigint-only primary key and existing event ordering relies on it. A partitioned parent needs a primary key including the partition key, data copying/table replacement, index migration and automated future-partition/default-partition maintenance. This run forbids deleting existing objects and cannot perform live DB verification in its sandbox. Keep the table intact and add an indexed `(job_id,kind,id DESC)` lookup now. A future migration should preserve global event ordering and audit history, establish partition creation/retention, and validate against a real backup before replacement. No retention deletion is introduced here.

## Operational consequences

Apply migrations before starting the updated server or CLI. With the server stopped, writes leave durable projection/CV queues until `jp admin project` or server restart drains them. Daily backups now contain `jobpilot.dump` plus `vault.tar.gz`; extract into a fresh directory, then pass the extracted dump to the existing restore script. Restore the vault separately into a fresh path before switching configuration. New bundles preserve uncommitted notes, git history, symlinks and target objects. Native PostgreSQL logs rotate hourly over weekday/hour filenames with 0600 permissions; launchd startup logs remain private and large existing logs are archived on initialization. The backup installer sets both StandardOutPath and StandardErrorPath. No existing launchd files or data are changed merely by editing these scripts.
