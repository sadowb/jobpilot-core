# ADR 0009 — Browser hands with server trust boundaries

Date: 2026-10-10. Status: accepted. Follows ADRs 0006 and 0008.

Workers need to recover from banners, custom menus, modals and non-native wizard controls without immediately asking the user. The user explicitly permits arbitrary non-secret field values. Deterministic preparation, verification and server-written hash-bound approval remain the submission authority.

Expose a fixed agent-browser interaction catalogue through `jp`, scoped to `JP_JOB`. Actions hold the existing browser lock, use the existing driver/pacing, count durable per-job attempts (including snapshots, failures and reconstruction), and audit verb/success without field values or browser error output. There is no command passthrough or agent eval. Sessions retain their network allowlist; URL navigation and tab selection additionally require the exact job host and HTTP(S). Page origin is checked before and after hands dispatch. A drift to another host hands off to the user. Existing manual board policies, including Workday, remain manual.

Refs are resolved by backend-authored DOM markers and agent-browser `get attr`. The backend checks the resulting unique element and dispatches its canonical selector. Native submit/image controls, recognized final-action names, and descendants are refused. Capture guards also block final-control pointer/key activation, implicit Enter, form submit events and `submit`/`requestSubmit`. Recognized unique final Submit/Send/Finish controls may be native or custom buttons. Only gated `browser submit` removes the guard after recording the durable submit fence; its optional selector must identify the code-selected final control. Protected account login can remove the guard only for an unambiguous password form with one Login/Sign in submit control. Ambiguous final controls remain a trust-boundary handoff. This is DOM control fencing, not interception of a site's arbitrary JavaScript or network requests.

Typing checks password type plus autocomplete, name, id, placeholder, ARIA/HTML labels and login context. Credential values cannot become agent plan rows. Secret tools remain origin-bound. Snapshot/element output is marked untrusted and bounded; known credential field values are redacted. Screenshots return a fixed file path under the job directory through the projection writer, and refuse populated credential fields. Upload accepts no model path: it selects the current validated job CV object with its required filename.

Every dispatched hands mutation invalidates verification before execution and increments a form revision. The verified hash includes that revision, field inventory, planned values, observed read-back and CV content address. Retrying an edit with the same value still needs a new approval. All entered text is kept in `job_forms.agent_edits`; current field values are represented in the ordinary plan with `source=agent`. Inventory/planning rebuilds preserve these values, including orphaned entries: unmapped edits cannot pass verification. Human answer updates supersede matching active agent edits while retaining their history. Multiple-select choices are stored/read back as JSON lists. Hash schema changes require re-verification/re-approval of older drafts.

Store successful normalized preparation commands before the first inventory, per-page interaction sequences, and safe hands Next/Continue transitions by page. Closed-session reconstruction replays only these server-recorded commands under origin, credential, submit, pacing and action-cap checks, then uses the deterministic inventory/read-back verifier. CV replay resolves the current object again. No agent can supply a replay array. A changed or unreconstructable UI cannot obtain automatic submission approval coverage. Modals in the active document, unnamed/contenteditable fields, and ARIA combobox/checkbox/radio controls are inventoried. Changed custom values enter agent plans; open comboboxes, placeholders and indeterminate checkboxes cannot pass read-back. Reconstruction replays the page sequence before deterministic native filling; custom fields must already match their stored values. Installed agent-browser help/core reference has no frame-selection verb; refs outside the active document are refused rather than extending trust across frame origins.

Keep one work order per model call by default. Recovery calls, or opted-in goal calls, receive the whole application goal, reviewed board recipe and runtime tool catalogue. A no-progress fingerprint covers meaningful form/state changes and ignores event chatter and revision-only changes. Failure → one same-model retry → one Sonnet retry → user handoff. Each call reserves the existing daily USD/token allowance and obeys its per-call USD budget and configurable timeout. Escalation model configuration accepts Sonnet ids only; the browser driver refuses Opus. Environment/auth failures still stop the pool, and exhausted daily admission budgets retain the existing requeue behavior.

Migration `0008_browser_hands.sql` adds action counters, edit/replay/revision columns and pending recipe suggestions. `recipe` stays read-only; `recipe suggest` can only add a pending row for the assigned job's board. Only the authenticated human-session/CSRF review route writes a reviewed recipe, with automation stopped and leases drained. Acceptance requires the human-reviewed full text and atomically replaces the file; an unsuccessful DB commit after replacement is repairable by reviewing again. Suggestions never enter worker prompts automatically.

New persisted runtime settings (environment equivalents use the snake_case Settings names):

| Setting | Default | Constraint |
|---|---|---|
| `browserMaxInteractiveActions` | `80` | 0–10000; lifetime per job, survives rebuild/resume |
| `browserEscalationModel` | `claude-sonnet-5-5` | `claude-sonnet-<numeric version>`; never Opus |
| `browserGoalRuns` | `false` | Goal calls opt-in; recovery calls always have the goal |
| `browserRunTimeoutSeconds` | `240` | 30–540, below the 600-second lease interval |

Settings updates retain the stopped/drained rule. No frontend, live database, site submissions, commits or pushes are part of this change.
