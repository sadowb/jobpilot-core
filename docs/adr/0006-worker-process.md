# ADR 0006: separate worker process and durable admission controls

Status: accepted by user decision, 2026-10-10. The existing `0004-review-hardening.md` and batch 2 ADR 0005 are retained.

The HTTP scheduler previously owned the automation flag, counters and pacing in memory. API restarts lost control state, and separate CLI claimers bypassed pacing. The worker pool now runs through `bin/jp-worker`; HTTP retains its projection/cleanup sweep and communicates with workers through PostgreSQL.

`automation` stores the desired enabled flag (default false). Start/Stop and claims serialize on that row. Settings changes require disabled automation and no live leases. A one-second supervisor polls the flag and publishes process status; ten-second heartbeat expiry marks processes offline. Worker names include the process ID. SIGTERM/SIGINT stop claims; bounded subprocesses finish their current step, then owned leases are released. Crash recovery still uses lease expiry and the existing submit-click fence. A worker environment failure disables automation with a system audit event.

`domain_pacing` persists the last reserved browser hit. All job browser commands, including a newly admitted job's first action, reserve a time atomically, commit independently of job transactions, then wait outside that pacing transaction. This also covers operator `jp next` and direct browser tools. No in-process pacing map remains.

Correction, 2026-10-12: admission must neither wait for a quiet domain nor write `last_hit`. Browser actions reserve future slots with `greatest(last_hit + gap, clock_timestamp())`; a cooldown predicate on admission therefore starves queued jobs while other agents keep using that domain. Resetting `last_hit` on a claim also discards outstanding action reservations. Free worker/browser slots admit queued jobs on the next dispatch pass, subject to the existing budgets, board caps and other admission gates. Their browser starts/first actions join the same `pace_browser` queue as every other action, preserving one reserved action per `domainGapSeconds`. Claims add no pacing reservations, so admissions alone cannot grow the pacing queue, including repeated dispatches whose leases expire without a worker starting. Agent processes may start together; domain requests remain spaced by the single persisted action reservation authority.

`cost_ledger` plus unsettled `budget_reservations` supply UTC daily admission totals. Claims check available allowance; each browser/CV model call atomically reserves the per-call maximum USD and configured token allowance under the same lock used for cost settlement. Reported usage settles the reservation transactionally. Crashes, timeouts and unparseable usage retain reservations until that day's quota resets. Token allowances cannot constrain the CLI's actual input/output tokens: one call can exceed its reserved allowance; its full reported usage stops later admission. The USD ceiling remains the installed CLI's per-call budget enforcement, not an independent billing guarantee.

Per-employer correction, 2026-10-12: `jobs.pacing_hostname` is a pacing key, despite its historical name. The pure `domain.canonical.pacing_hostname` function uses `host/tenant` when a board adapter resolves a tenant on a known shared ATS endpoint (Greenhouse, Ashby, Lever, SmartRecruiters, Workable, or Workday's shared `myworkdaysite.com` hosts). Single-employer subdomains, custom domains, unknown embedded tenants and local hosts retain the bare host. Tenant segments are ASCII letters/digits, hyphens or underscores, start with a letter/digit, are at most 100 characters, and normalize to lowercase; anything else falls back to the host. Host-only checks always parse the host part, so a tenant cannot turn a remote board into a local pacing exemption. Native browser events that supply a bare host reuse the job's tenant key on that same host.

Each employer board retains one reserved action per `domainGapSeconds`. For a positive gap, the total shared-host action rate is now at most `workerConcurrency / domainGapSeconds` (for example, four workers and a five-second gap allow up to 0.8 actions per second). This trades more employer parallelism for more requests from the same IP to one ATS vendor; there is no extra aggregate host throttle. A zero gap disables time pacing and has no finite time-based rate bound. Daily board caps and admission budgets are unchanged. Migration `0019_pacing_per_tenant.sql` runs a Python hook through `bin/jp-migrate`, re-resolves each effective application URL, and inherits the latest host, previous-key or destination reservation with `greatest`; it retains host rows for jobs with unknown tenants and never moves a reservation earlier. Rerunning the hook is idempotent. Apply migrations with automation stopped and leases drained.

The API keeps existing automation fields and adds `workerOnline`, `idleReason` and `budget` to JSON/SSE. Frontend rendering is deferred by the explicit prohibition on frontend source changes. This limitation is recorded in the handoff.

The launchd plist uses KeepAlive, private `data/` logs and a 600-second exit timeout. It is a template, with this workspace's absolute paths and tool PATH. The orchestrator must apply migration 0003, check paths/log directory/tool authentication, and install/load it. KeepAlive can restart an enabled worker after SIGTERM; disable automation first when stopping work permanently.
