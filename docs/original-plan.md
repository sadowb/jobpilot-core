# Plan: JobPilot — parallel, token-cheap job-application system with local dashboard

## Current implementation (2026-10-12)

ADR [0015](adr/0015-direct-browser-harness.md) supersedes the browser-agent constraints below for direct mode, now the default persisted `agentMode` setting. One Celery job task runs Claude Haiku 5.5 once with only Bash authorized for `bin/jp-harness`. The deny-default macOS sandbox contains model-authored Python and the inherited browser-harness daemon; Chrome remains free through loopback CDP. The runner prepares a recorded shared-Chrome tab, selected CV path and secret-filtered owner DATA. Strict bounded result JSON is mapped through services and the state machine into reported drafts, missing questions, owner handoffs or reported submissions. Direct drafts use `job_forms` and a server-computed hash with explicit agent-reported provenance. The dashboard labels these as “filled by the agent (reported, not code-verified)”. Approval creation remains human-only; authorized submit runs commit the click fence before model execution. Unapproved reports are recorded as submitted-as-reported and surfaced in Needs You. No browser-level final-submit guard or per-action pacing applies in direct mode. Admission, leases, concurrency, recorded browser cap, daily budget, board caps, stop/drain and task accounting remain shared. Extra tabs are reaped and may transiently exceed the recorded cap. Toolbox remains selectable, with all existing deterministic checks and shim restrictions; external tracker capture retains that path. See ADR 0015 for enforced boundaries and live validation requirements.

Owner decision (2026-10-12): a direct run fills a whole application and has no per-run work cap by default. `browserBudgetUsd=0` / `browserRunTimeoutSeconds=0` omit CLI budget and subprocess timeout; explicit non-zero limits remain supported. `run_job` has no Celery soft/hard deadline; control tasks remain bounded. The direct subprocess monitor renews the 600 s lease every 15 s on a short independent autocommit connection, checks Stop every second and drain every poll, and kills the Claude process group on cancellation or lost ownership (SIGTERM, then SIGKILL after up to 5 s). The only default automatic inactivity stop is `agentStallSeconds=900` (zero = off): real streamed stdout, including partial messages, resets it; DB heartbeats do not. Only the final CLI result text reaches `parse_result`, while final usage reaches the ledger. Preparation interruption/stall returns queued without refunding the started attempt; authorized submits become submission uncertain, never retried. Daily USD/token budgets continue to gate new admissions: an unlimited run reserves the finite CV USD allowance plus the token reservation, settles actual usage on completion (unknown usage gets the reserved estimate), and can overshoot daily totals while running. See ADRs 0012 and 0015 for the monitor, reservation/rollover semantics and live validation limits.

ADR [0003](adr/0003-fastapi-backend.md) supersedes the original Node backend choices below. Backend: Python 3.12, FastAPI, psycopg 3, pydantic v2, `logging`, strict mypy and ruff (lint + format). Frontend remains Vite + React + strict TypeScript; its toolchain is separate. SQL migrations run through `bin/jp-migrate` **before workers**. CI now runs Python lint/format/typechecks, frontend typecheck/build, dependency audits and Gitleaks (batch 3). ADR [0012](adr/0012-celery-redis-execution.md) supersedes the hand-rolled worker thread pool and scheduler with Celery and a Redis broker on `127.0.0.1:6380` (broker-only, non-durable; PostgreSQL remains authoritative).

Current backend package: `backend/src/jobpilot/{api,controller,service,repository,entity,dto,config,middleware,domain,boards,browser,projection,secrets,worker}`, with `server.py`, `actions.py`, `cli.py` and `migrate.py`. HTTP routing, authentication and request/response contracts are separate modules; feature services share the typed `service/application.py` facade. See [codebase guide](codebase-guide.md) and [ADR 0010](adr/0010-spring-style-layers-api.md). Services owns business writes and their audit events; global configuration/account events use a nullable `job_events.job_id`. The CLI uses one main connection per invocation (paced browser commands use a short independent connection); the server uses a pool opened at lifespan startup. `AgentDriver` is implemented by `worker/claude.py`; the execution runner and Celery tasks (`worker/{app,tasks,runner,runtime,client,names}.py`) replace the former in-process thread pool (ADR 0012).

Every JSON route has a pydantic response model. Streaming/file routes explicitly disable JSON response validation. OpenAPI is exported offline with `backend/.venv/bin/python backend/scripts/export_openapi.py /tmp/openapi.json`; the authenticated Swagger UI and schema are available at `/docs` and `/openapi.json`, using self-hosted assets and the existing browser session. Canonical routes use `/api/v1/`; `/api/` routes remain compatibility aliases outside the schema. `GET/PUT /api/settings` persists concurrency, models, effort and per-call budgets, daily cost/token admission limits and domain pacing; writes require a UI session, stopped automation and drained leases. `/api/needs-you?limit=50&offset=0` pages both lists independently (maximum 200).

Vault notes are eventually consistent: job/application triggers queue dirty jobs in the same transaction as the authoritative write. Both HTTP and the standalone worker supervisor own independent two-second maintenance threads, including while automation is stopped; the worker keeps projections, CV commits and orphan browser cleanup alive without HTTP. Slow sweeps do not block worker heartbeats. Generation checks plus per-job advisory locks prevent stale projection acknowledgements; a global session advisory lock serializes CV queue reads/commits across processes, and browser cleanup rechecks state under its existing per-job lock. Failed work stays queued and is logged. `jp admin project [jobId]` requests and performs a repair pass. CV commit queues call the single writer `projection.commit_cv`: `.tex` objects and job links are committed during preparation; PDFs for all track versions and jobs at submit. Tailored jobs now symlink immutable objects too. Daily backups bundle `pg_dump` and a full vault tar (including uncommitted notes and CV targets), retaining 14 private bundles across plaintext and optional age-encrypted formats. See SECURITY.md for encryption and recovery.

Worker browser sessions close on blocked/idle/terminal state, successful lease release or expired leases, except that `awaiting_approval` jobs retain their filled browser session. The agent stops and releases its execution slot while the browser remains available for approval; raw widget and authentication state cannot always be rebuilt from the saved plan. Maintenance preserves these sessions even when their task is blocked or its lease expires. Explicit close requests and archiving still permit cleanup. Cleanup is requested in the job transaction and attempted after commit; failures remain tracked for retry, and eligibility is rechecked under the browser lock. An active model's lock prevents cleanup during its run. Submit and confirm retain the same live session while the lease is held. After approval, the existing session is verified before any click. If the browser has disappeared, the saved form is reopened and deterministically refilled, then checked against the approved hash; forms that cannot be safely rebuilt require human review. Retained approval sessions still consume memory and are not bounded by worker concurrency. Human review uses dedicated Chrome at :9223 with `data/chrome-review` as its user-data-dir, or explicitly configured attach at :9222 (`reviewBrowser` setting, UI-session-only browser-review endpoint). Automated workers retain isolated allowlisted sessions: installed agent-browser rejects `--allowed-domains` together with profile/CDP. See [ADR 0005](adr/0005-runtime-architecture.md) for this boundary and the monthly event-partitioning deferral.

The catalogue now exposes scoped `status`, `cv check`, `cv use`, `answer match`, `done` and deterministic `browser next-page`. CV verification checks the job's registered TeX/PDF content address, Overleaf lint, one page and confirmed fact citations inside TAILOR regions. Base-track switching is limited to base-mode, pre-ready jobs on non-manual boards. Completion requires an idle work gate and an owned lease. Answers remain code-planned; matching returns keys/IDs only.

Migration 0006 adds UTC-day board caps for preparation admission, browser calls and account creation (defaults 200 / 10,000 / 20). Claims reserve preparation under the existing admission lock and stop a board when any cap is exhausted; actual browser/account operations reserve atomically before execution. The gated final click and confirmation readback remain available across board caps. `idleReason` reports exhausted board caps, and the Boards API exposes `maxPreparePerDay`, `maxBrowserPerDay`, `maxAccountPerDay`; changing them requires stopped automation and drained leases.

Supported forms have at most 20 pages, a unique visible Next/Continue button explicitly typed `button`, distinct deterministic inventories and a reproducible route from the job URL. Fields are indexed/namespaced by page. Fill and verification replay all pages; approval hashes cover inventories, planned and observed non-secret values, and the CV. A final page requires a unique visible enabled submit control. Unsupported/ambiguous navigation, custom widgets, empty review pages and resume-only forms hand off. Workday is forced manual even for existing auto board settings. OS-authenticated account reveal remains skipped because a native LocalAuthentication helper is unavailable. See [ADR 0007](adr/0007-catalogue-caps-pages.md).

The original decisions and proposed tree below are retained for history; annotations identify superseded choices and outstanding plans.

## Context
Old setup (`~/Job Applications/.pi`, `~/wiki/job-tracker`) works but: dense SKILL.md read every run; thin CV method; Greenhouse-only dedup (`workflow.py:greenhouse`); non-atomic `create()`; overloaded frontmatter; ~9 evidence files per role (logs explode at scale); Pi-specific; sequential; no UI beyond an Obsidian Base.

Goal: new project in `~/jobsClaude`: a real **PostgreSQL database with proper relational tables** as the system of record, an **Obsidian vault** as the human-readable view + CV files, a beautiful local dashboard, and workers that push thousands of applications through **in parallel** with Haiku 5.5 using minimal tokens. The agent never writes queries or reads files: it calls **ready-made tools (`jp`)** that already know the schema. Agent-neutral (Claude/Haiku first, Hermes pluggable).

Decisions (user): dashboard + approvals + automation; new schema + new vault; ~~Node~~ (superseded by Python/FastAPI, ADR 0003) + Vite/React; production-ready + secure; no unit/integration tests; verify via native Claude browser; GitHub repo for `~/jobsClaude`; **Haiku 5.5 (`claude-haiku-5-5`, medium) does browsing, form interaction, applying through to submission, and tailored CV writing**; ~5 CV tracks with per-job tailor/don't-tailor; "About me" in UI; every applied role + date saved; CV always `Abdelhadi Marjane.pdf`; CV versions in git; symlinks not copies; **PostgreSQL** (proper DB, proper tables, persisted; no Docker needed); **agent-browser** CLI for the browser (not Playwright); **deterministic runtime verifiers** because Haiku can't reliably notice its own mistakes; UI design in Claude Design by **Sonnet 5.5 (xhigh for design system, high for screens)**; folders named `backend`/`frontend`; agent may create accounts safely; UI designed in **Claude Design**; **Opus 5.5 reviews the finished work against this plan**; scale 5k+ jobs.

## Research findings that shaped this
- Monorepo practice: split deployables (frontend, backend) from shared code; share **API contracts only**, never DB row types (type leaks); shared code must earn its place; pnpm workspaces with `workspace:*`. ([pnpm monorepo guide](https://www.wisp.blog/blog/how-to-bootstrap-a-monorepo-with-pnpm-a-complete-guide))
- AIHawk (28k★ job bot): LinkedIn bans + legal threats removed its main feature → **platform-policy risk is the #1 failure**; config sprawl in YAML. Lesson: per-board automation policy; default LinkedIn/Indeed = assisted/manual, not autopilot. ([ERE](https://newsletter.ere.net/p/what-it-means-to-apply-for-a-job-is-changing-0c55), [ostechnix](https://ostechnix.com/automate-job-search-in-linkedin-with-ai-and-linkedin_aihawk/))
- Agent credentials: keep secrets in a vault, model sees placeholders, runtime injects at the browser layer, domain allowlist, task-scoped, human approval, audit log. ([1Password](https://blog.1password.com/closing-the-credential-risk-gap-for-browser-use-ai-agents), [Notte](https://www.notte.cc/glossary/browser-identity/what-is-credential-vaulting-for-ai-agents), [Infisical Agent Vault](https://infisical.com/videos/how-agent-vault-works-video-page))
- Postgres queue: `FOR UPDATE SKIP LOCKED` + lease (`visible_at`) + heartbeat; claim then commit, don't hold a transaction during the job; at-least-once → idempotent steps. ([slonq](https://pypi.org/project/slonq/), [SKIP LOCKED](https://www.netdata.cloud/academy/update-skip-locked/))

"Hexagonal / ports" in plain words: `domain/` holds rules and never touches Postgres, the web, or the browser directly. ## Data architecture
- **PostgreSQL = system of record**, native (no Docker). Already on this Mac: `/Applications/PostgreSQL 16` + Postgres.app. Plan: a **dedicated cluster** for JobPilot in `~/jobsClaude/data/pgdata` on its own port (5433, localhost only, so it can't clash with your other Postgres), started by a **launchd agent** (auto-start on login, auto-restart on crash). Persistence/crash-safety = normal on-disk data dir with WAL + `fsync` on (the default), daily `pg_dump` to `data/backups/`, restore script. Docker is installed but its daemon isn't running — avoiding it removes a failure point. ~~Drizzle ORM + `drizzle-kit` migrations run as a separate step before workers.~~ Superseded by psycopg and forward SQL migrations via `bin/jp-migrate` (ADR 0003). Readable relational tables: `companies`, `jobs`, `applications` (role, company, `applied_on`, `applied_at`, cv_version, confirmation), `job_events` (append-only audit/step log, indexed; monthly partitioning planned but deferred in ADR 0005), `tasks` (queue), `cv_tracks`, `cv_versions`, `profile`, `facts`, `answers`, `approvals`, `accounts` (site, username, secret_ref — no secrets), `cost_ledger`, `boards`.
- **Obsidian vault = one-way generated view + CV files.** Projector writes `Job.md` frontmatter from DB (so Bases give the Excel-like view); body below `<!-- notes -->` is yours and never overwritten. Frontmatter edits in Obsidian are not synced back (change them in the UI) — deliberate, avoids two-way-sync bugs. Notes ↔ DB stay separate.
- **IDs generated by backend code, never the agent**: `id = "j_" + base32(sha256(canonical identity))[:8]` (canonical URL, or `board|tenant|req_id`); unique constraint; dedup = indexed lookup (url hash · board/tenant/req · normalized company+title+location).
- **Agents never write SQL.** Direct-mode Python reads only its selected CV and sandbox runtime/state paths. Toolbox agents never read files; the backend ships a fixed toolbox (`jp …`); each tool is one prepared, indexed query/transaction returning a tiny JSON digest. `jp tools` prints the live catalogue (also embedded in `agent/AGENTS.md`).
- **Git (vault repo) = CV versions only**: `.tex` always, PDFs for track versions and submitted jobs; committer batches; messages `cv(<track>): …`. Per-job/step history is the `job_events` table (no log files, no VERSIONS.md).
- Backups: `pg_dump` daily to `data/backups/`, bundled with the vault tar; 14 bundles, mode 0600.

## CV system (minimal generation)
- Always `Abdelhadi Marjane.pdf`; store objects immutable + content-addressed; base jobs and track "current" are symlinks → one PDF+tex serves thousands of jobs; `cv_versions.sha256` pins what each job used.

- `cv_mode` per job (default per track/batch): `base` (zero LLM) or `tailor` (Haiku 5.5 medium edits only `% BEGIN TAILOR` regions; input = requirement digest + fact ids + region text; cached by track-version+requirements-hash; identical result → symlink).

## Parallelism
- Postgres queue: transactional-outbox pattern with Celery + Redis (ADR [0012](adr/0012-celery-redis-execution.md)). `dispatch` (in `bin/jp-control`) claims under the `automation` row lock with `UPDATE tasks … FOR UPDATE SKIP LOCKED` (90 s dispatch lease), then after commit publishes `run_job(job_id)` to Redis. Lossy broker: lost messages recover when the 90 s lease expires. `bin/jp-worker` starts atomically (`started_at IS NULL AND leased_by = <task id>`), extending lease to 600 s. PostgreSQL remains the authoritative system of record.
- **Browser = `agent-browser` CLI** (found: `~/.npm-global/bin/agent-browser`, v0.38.2, npm global; supports `--session NAME` isolation, `--cdp`/`--auto-connect`, `batch --bail`, `snapshot -i`, `fill`, `eval`, `upload`). Each job gets its own named session → N Haiku workers run side by side. The backend wraps it in `jp browser …` commands so the agent gets few, safe verbs and secrets are injected inside the wrapper (agent never receives them).
- **Original Chrome plan (superseded in part by ADR 0005)**: a Chrome with CDP is already listening on `127.0.0.1:9222` (your personal Chrome). Default = a **dedicated JobPilot Chrome profile** (own `--user-data-dir` + CDP port) so mass runs don't touch your personal cookies/tabs and credentials stay isolated; Settings option to attach to your 9222 Chrome instead (matches the old workflow rule; asks first).
- **Why not the native Claude browser**: it is the desktop app's single shared pane, bound to a GUI session — it can't be driven by background/headless Haiku workers, has no per-job isolated sessions, no secret-injection hook, and runs one page at a time. It stays our tool for *verifying the dashboard UI*, not for mass applying.

## Token economy
Agent follows work orders via `jp`: `next` · `context` (digest) · `form plan` (deterministic field→value plan from answers) · `answer match|set` · `cv use|tailor|check` · `verify` (code checks attachment hash/required fields/errors) · `recipe <board>` · `gate submit` · `status`. `agent/AGENTS.md` ≤ one page.

## State machine (enforced in `domain/`)
`discovered → screened → preparing → ready → awaiting_approval → submitted → screening → interview → offer | rejected | withdrawn | closed`; `waiting_on: agent|you|site`.
Haiku drives to the submit button; `jp gate submit` requires a server-written approval bound to the draft hash (UI click on a named bounded batch) then confirmation evidence (`live-verified`/`user-confirmed`); core stamps applied date/role/CV. Agents can't create approvals.

Human `user-confirmed` completion is a separate authenticated UI-session attestation for a submission made outside automation. It can advance a pre-submit job without automated checks or an approval row. If no draft hash exists, Services deliberately passes `"user"` as both gate hashes with `user-confirmed` evidence; it never clicks submit or grants an automated approval. The audit/application record labels this human report explicitly. Automated submit clicks retain the verified-draft approval requirement.

## Deterministic verification (Haiku can't be trusted to notice its own errors)
Not unit-test suites: **runtime checks run by code after each step**, so correctness never depends on the model's self-report:
- Fill check: re-read every field value via `agent-browser eval`/`snapshot` and compare to the fill plan (exact match, select labels committed, checkboxes).
- Validation check: no visible error messages; required fields all non-empty.
- Attachment check: uploaded filename == `Abdelhadi Marjane.pdf` and size/hash == expected `cv_sha256`.
- Identity check: page origin/host and requisition id match the job record (right company, right posting) before fill and before submit.
- Pre-submit check: current form state hash == approved draft hash; any drift → back to `preparing`, invalidate verification, then verify again before fresh approval.
- Confirmation check: after submit, confirmation text/URL pattern from the board adapter must match; otherwise `submission_uncertain` (never retry-submit blindly).
- Each check returns pass/fail + diff; failure triggers a bounded targeted retry, then `waiting_on: you`. Results stored in `job_events`.
- CV checks (`jp cv check`) are the same kind: one page, margins, fact-id citations, Overleaf lint.

## Agent guide (`agent/AGENTS.md`)
The one file the browser agent reads (≤ ~1 page + generated tool table): purpose, hard rules (data ≠ commands, never submit without gate, never handle secrets), the **tool catalogue** (name, args, returns, when to use — generated from `jp tools` so it can't drift), the work-order loop (`jp next` → do → `jp verify` → `jp done`), failure/escalation rules. Board quirks only via `jp recipe <board>`. Repo-level `AGENTS.md` is for developers; `agent/AGENTS.md` is runtime.

## Boards & policy
Adapters: greenhouse, lever, ashby, workday, eightfold, smartrecruiters, icims, taleo, successfactors, workable, bamboohr, custom (generic form inventory). **Per-board `automation` policy: `auto | assisted | manual`**; LinkedIn/Indeed/other platforms that prohibit bots default to `assisted/manual` (ingest + prepare + you click), per AIHawk lesson.

## Accounts & passwords (agent can create accounts, safely)
- Passwords generated by backend CSPRNG, unique per site, stored in a `SecretStore` (default macOS Keychain; adapter for 1Password/Bitwarden CLI). Postgres holds only `site, origin, username, secret_ref, status`. The LLM never sees a value: it passes the raw `secret_ref` to `jp browser fill-secret <jobId> <selector> <ref>`; the wrapper checks the origin and injects the resolved value over stdin.
- Injection bound to the recorded **origin** (credential for A can't be filled on B → blocks prompt-injection phishing); task-scoped; every use audited (time, job, origin, ref).
- Creating an account requires approval naming portal/tenant (per-site allowlist you maintain in Settings, or per-batch approval); ToS/consent acceptance is part of that approval. CAPTCHA/MFA/email-code → `waiting_on: you`; no bypass; inbox reading off by default (optional scoped verification-mail reader later).
- UI **Accounts** screen: list, status, reveal-on-demand behind OS auth, delete; no bulk export. Never log/store secrets in DB, vault, git, prompts, events.

Screens: Today · Pipeline (Excel-like table + kanban, server-side paging) · Job detail (posting, requirement→evidence, timeline from `job_events`, CV preview) · Needs-you (answers, CV + submit approvals, account-creation approvals) · Automation (paste URLs → track + tailor option → Prepare; live parallel feed, pause/retry, cost) · About me · CV Tracks (history from git) · Accounts · Settings (vault, model, workers, budgets, board policies).

## Security / production-grade
- Backend 127.0.0.1; Host/Origin allowlist, CSRF, per-start API token (CLI+UI), strict CSP, sanitized markdown; approvals only via authenticated UI route; paths confined to vault root, symlinks only into `_cv-store`.
- Postings/sites = untrusted data (prompt injection): inert rendering; agents told data ≠ commands.
- ~~Zod validation at every boundary; schema versions + migrations; pino logs; ADRs; TS strict, ESLint/Prettier;~~ Backend choices superseded by pydantic + SQL migrations + Python `logging` + strict mypy + ruff; ADRs retained. Frontend remains strict TypeScript with its own tooling. Implemented CI: ruff lint/format, strict mypy, frontend typecheck/build, pip-audit, pnpm audit and Gitleaks; an exact Python requirements snapshot and pnpm lockfile, weekly Dependabot; Postgres bound to localhost with generated password in `.env` (gitignored).
- Worker spawns agents with arg arrays, scoped cwd, optional per-run timeouts/budgets and direct-mode lease/stall monitoring. Haiku guard: deterministic plans + code verifier; repeated failure → `waiting_on: you`.

## Phases
0. Scaffold; `git init ~/jobsClaude`; create private GitHub repo; first commit (confirm before remote/push).
1. Postgres schema + `domain` + `db` + `projection`.
2. `cli` (`jp`) work-order tools.
3. `http` + SSE + approvals.
4. Claude Design pass → `frontend`.
5. `worker` + `jp browser` wrapper over agent-browser + secrets + verifiers + Haiku 5.5 / Hermes drivers.
6. `boards` + `agent/` kit + AGENTS.md files.
7. Dry run through `awaiting_approval` (nothing submitted).
8. **Opus 5.5 (`claude-opus-5-5`) review**: an agent reviews the finished implementation against this plan, lists missed edge cases (concurrency, crash recovery, credential leaks, dedup misses, symlink/path escapes, board-policy gaps), fixes applied.
9. Optional: one-way importer from old tracker (off by default).
